# Skill 设计的几个核心问题

## Skill 是什么

Skill = agent 已有能力与特定任务之间的**知识差的精确补丁**。

Agent 有通用智能，但缺少特定领域的规则、工具接口、质量标准。Skill 的全部价值就是精准填补这些缺口——不多也不少。

## 第一原则

> **只提供 agent 无法可靠地自发产出的最小知识集，以最低认知负担的形式交付。**

"可靠"是关键词。"知道"不等于"每次都会做到"。

## 三种知识差距

Skill 填补的差距分三种，需要不同的写法。

**知识盲区** —— agent 完全不知道。你的内部 API、独特的业务流程、自建工具的调用方式。

- Skill 作用：注入新知识
- 设计重心：准确、完整
- 载体：速查表、命令示例

**激活缺口** —— agent 知道，但不会在对的时机想起来用。比如 agent 理解辩证法，但面对复杂问题时不会主动做矛盾分析。Skill 不是在教知识，是在建立触发机制。

- Skill 作用：建立触发模式 + 执行脚手架
- 设计重心：触发条件要精准。description 和"何时使用 / 不适用场景"是核心资产，方法本身反而可以简练——agent 被激活后自己知道怎么展开
- 载体：触发条件、执行脚手架

**一致性缺口** —— agent 有时做得到，但质量不稳定。比如 agent 会写好文章，但没有锚点时结论前置时有时无、克制程度飘忽。Skill 把行为质量的方差压下来。

- Skill 作用：锚定质量标准
- 设计重心：正反对比和自检清单比原则阐述更有用——agent 不需要被说服，需要执行时的锚点
- 载体：正反示例、自检清单

| | 知识盲区 | 激活缺口 | 一致性缺口 |
|---|---------|---------|-----------|
| Agent 状态 | 完全不知道 | 知道但想不起来 | 有时做到有时做不到 |
| 删掉 Skill 后 | 完全做不了 | 不会主动做 | 能做但质量飘忽 |

一个 Skill 通常同时包含多种差距。意识到"这一段在填哪种差距"，有助于选对写法。

## "不写"是最重要的设计决策

写 Skill 最大的诱惑是写太多。噪声的害处不只是浪费 token——它稀释真正有价值的信息，让 agent 更难抓住重点。

检验标准：**把这句话删掉，连续 10 次调用中，agent 的行为质量方差会增大吗？** 不会就删。

典型噪声：

- "先理解用户需求" —— agent 本来就会
- "用清晰的语言表达" —— agent 本来就会
- 每个意图举 3 个路由示例 —— agent 本来就能做意图分类
- 多步 API 编排的自然语言伪代码 —— 应该固化在脚本里

## 所有 Skill 的共性结构

不管什么类型，好的 Skill 都回答四个问题：

1. **什么时候用？** —— 触发条件 + 不适用场景
2. **核心知识是什么？** —— agent 缺少的规则 / 接口 / 标准
3. **做完长什么样？** —— 输出规格或质量标准
4. **怎么知道做错了？** —— 常见错误 / 反面案例 / 自检清单

1 和 4 最容易被忽略，但最值钱。**边界定义（尤其是"不适用场景"）比方法描述更能防止 agent 犯错。**

## 三条设计约束

**边界先于内容。** 先定义"什么不是这个 Skill 该做的"，再写"怎么做"。没有边界的 Skill 是什么都想管但什么都管不好的通用指引。

**形式服从消费方式。** Agent 读 Skill 是为了快速提取可操作的知识。规则用表格，接口用命令示例，流程用编号步骤，标准用正反对比。散文是最差的载体。

**一个 Skill 解决一个问题。** 如果 description 需要用"和"连接两件事，大概率该拆成两个。

## 未解决的问题

1. "激活缺口"和"一致性缺口"在实践中有时很难区分。是否需要这么细的分类？合并为"agent 知道但做不稳"够不够？

2. 多个 Skill 形成体系时（如矛盾分析法引用集中兵力、调查研究等），Skill 之间的关系应该怎么设计？

3. 除了"删掉后方差是否增大"这个思想实验，有没有更实际的方式验证 Skill 的设计质量？

4. 不同 agent 平台的 Skill 机制差异，会不会导致这些原则需要修正？
